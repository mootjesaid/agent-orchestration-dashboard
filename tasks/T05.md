# T05: Durable workflow state and transitions

Status: implemented, verified and independently reviewed. Updated 2026-11-18.

- T04 is deferred for T05 by user decision. T01–T03 capability gates remain applicable to runtime work.
- Requirements: FR02, FR06, FR15 in [PRD](../docs/PRD.md).
- Complexity: M (relative uncertainty, not a delivery promise).
- Agent recommendation: one executor using an available capable model, high effort;
  independent reviewer afterward. No parallel agent work by default.

## Objective

Persist workflow revisions and enforce state transitions independently of AI.

## Scope and relevant areas

Backend action, command and status enums, SQLite schema, and feature tests.

## Acceptance criteria

- [x] Persist workflow/request state, immutable revisions and ordered audit events.
- [x] Reject invalid/stale transitions through backend guards.
- [x] Conditional state updates and constraints prevent duplicate transition effects for competing commands on SQLite.
- [x] Transaction rollback leaves no partial state/event.
- [x] No agent or UI flag can fabricate plan approval.

T05 supports creation, request amendments, clarification and entry into planning.
Each accepted operation increments the workflow version and appends one audit event
with that sequence. Request text is stored as append-only revisions. Planning results,
approval, execution and recovery transitions require their corresponding later tasks.

## Validation and handoff

Windows PHP 8.5.12: Pint passed and all eight focused PHPUnit tests passed with
32 assertions. The version-race test interleaves two connections to one SQLite
file between the first command's read and its conditional update. It demonstrates
stale-write rejection after a competing commit. Native macOS was deferred.

Independent read-only Codex review identified UUID casing, SQLite revision
immutability and race coverage gaps. The follow-up review confirmed all three fixes
and reported no remaining findings within T05.

## Excluded scope and budget

No unrelated features, dependency upgrades or scope expansion. Installation, native sandbox
setup and new dependencies need specific approval. Budget: one focused task/role session;
record estimated token/time range and confidence before dispatch. Numeric estimates remain
unknown until T01-T03 establish measurements. Split L tasks at the named boundary before
implementation approval if they cannot be reviewed independently.
